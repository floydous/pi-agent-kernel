# Feedback on `pi-agent-kernel`

**Date:** 2026-08-28
**Subject:** `pi-agent-kernel` v1.0.0 — `@earendil-works/pi-coding-agent` extension
**Method:** Read all tool registration modules, the safety layer, the patcher, the post-edit verifier, and the tests; ran the full test suite (30 sections, all green); exercised the live tools end-to-end in an actual Pi session (the one this document was written in), including the epistemic guard, the patcher's three matching strategies, the syntax gate, the oracle, the search indexer, the repo-map, the AST search, and the hybrid code search.

This is opinionated, both pro and con. The negatives are at the end because the negatives are the part you asked for explicitly and I want the structure to match the priority.

---

## TL;DR

`pi-agent-kernel` is a serious, well-engineered power-user extension for Pi. The architectural discipline is real — small focused modules, explicit dependency injection, a per-session safety singleton, a custom TS delimiter-balancer that is genuinely faster and more useful than `tsc --noEmit` for per-edit gates, and a 30-section test suite that all passes. Three of its four big claims hold up under live testing. The fourth — the "Read-Before-Write Epistemic Guard" — works, but works in a way that is more permissive than its name suggests, and that gap is the single most important thing to fix. The most consequential design choice, documented in `docs/editing-and-verification.md`, is that **a patch which succeeds in matching but fails the syntax check is left on disk**. I think that is wrong and the project would be measurably better by inverting it.

I would recommend this extension to a power user of Pi, with two caveats: (1) understand the epistemic guard's actual definition of "inspected" before relying on it; (2) expect to need `/undo` after any non-trivial syntax-breaking edit, and prefer a branch or stash for anything risky.

---

## What I tested, and what I observed

### What worked well

**1. The test suite (30 sections, all green).** `npx tsx test.ts` ran the full suite, with the last section being section 25 (post-edit verification). No failures, no `✗` marks, no skipped sections, no warnings. The suite is a real, working signal — it covers not just the happy path but the gnarly cases (CRLF preservation, regex-literal detection in the syntax gate, per-session guard isolation, case-sensitivity regression on Windows vs. POSIX, undo preserving the working tree, prompt-cache partitioning of the compaction prompt, output clamping against a 40 KB minified line, multi-block patches, etc.). For a 6,400-LOC extension, this is a healthy test-to-source ratio.

**2. `get_repo_map` returned a useful, PageRank-ranked AST overview of the repo** in roughly 1k tokens. The output is the kind of orientation dump that would actually save context on a real task. The `epistemic_guard.ts`, `search_index.ts`, and `index.ts` correctly bubble to the top of the ranking — they have the most dependents. This is one of those small, well-implemented features that quietly earns its place.

**3. `ast_search` and `code_search` worked on the first try.** I asked for `EpistemicGuard` and got back a single, exact, type-correct hit with the body. I then asked a natural-language query ("epistemic guard read-before-write check") and got back five ranked hits with breadcrumbs, RRF/BM25/cosine scores, and chunk content — including a `VecCos=0.707` match from the embedder, which means the hybrid indexer is genuinely loaded and the model is not just BM25-pretending-to-be-semantic. The retrieval system is the most ambitious piece of the extension and it works.

**4. The patcher's three matching strategies.** Exact → whitespace-normalized → fuzzy similarity ≥ 0.85. I tested a case where the search block was byte-identical, a case where it had matching content but different surrounding whitespace (worked), and the "no match" case (correctly returned an error without writing to disk). The CRLF preservation behavior — normalize to LF, restore CRLF on output — is the right call and is exactly the kind of bug that bites hard on Windows if you get it wrong.

**5. The custom TS syntax gate is genuinely good.** I introduced an unclosed `{` and it was caught immediately, with a precise line-number message ("Unclosed '{' opened on line 2 (still open at end of file)"), and crucially, **the patch was reported as `FAIL!` and was not auto-committed to git**. The state machine that walks the source respecting strings, templates, block comments, line comments, and regex literals (with the `regexCanStart` heuristic for division-vs-regex) is a real piece of work. For per-edit gating it's strictly better than `tsc --noEmit` (which would take 5+ seconds and pull in the full project), and better than `node --check` (which can't parse TS at all). The comment in the source code says exactly this and is correct.

**6. The oracle.** `runOracle` runs a shell command, returns a structured `{passed, exitCode, durationMs, output, summary}` result, kills the whole process group on timeout (including the Windows `taskkill /T` path), and reports `GREEN [VERIFIED]` / `RED [EXIT N]`. I tested exit 0, exit 42, and a noisy 2000-char single line — all worked as designed. This is a small thing but it is *correct* in the way that matters: the user can ground "the tests passed" in real evidence rather than the model's self-report.

**7. The output clamper is doing real work.** I saw a 40 KB minified single-line file get clamped to 605 bytes, with the full raw output preserved at a temp path and a footer pointing to it. The model can still `read` the spillover file if it needs the full content. This is the right contract — bounded context, lossless fallback.

**8. Per-edit git auto-commit + `/undo`.** I observed `autoCommitFile` create commits with `pi: update <path>` messages, and `undoLastCommit` uses `git reset --mixed HEAD~1` (preserves the working tree, does not destroy uncommitted work). The test `section-08.1-undo-preserves-working-tree` exists specifically to lock this behavior in. This is good.

### What I think is genuinely wrong

These are ordered by severity. Items at the top can cause silent data loss or false safety; items at the bottom are taste and style.

#### Issue 1 (critical): The epistemic guard is not what its name promises

**The claim.** README: *"Epistemic Read-Before-Write (`src/safety/`) — Blocks hallucinated file mutations on uninspected files."* Section 13 of the test suite reinforces this. The `EpistemicGuard.checkReadPrecondition` error string says: *"You must ground your attention in the physical file contents first."*

**The actual behavior.** I tested four scenarios in a live session:

| Pre-edit state of file | Result |
| --- | --- |
| File created with `printf`, never read, never `grep`d, never `cat`d | **REJECTED** ✓ |
| File created with `printf`, then `ls`d via bash | REJECTED ✓ |
| File created with `printf`, then `cat`d via bash | ALLOWED ✗ |
| File created with `printf`, then `grep`d via bash | ALLOWED ✗ |

The guard's actual definition of "inspected" is "the file path was a token in a non-flag position of a bash command that looked at it, **or** the file was passed through `read` / `ast_search` / `code_search`." It is **not** "the model has seen and understood the contents of this file."

**Why this matters.** The whole epistemic story is the project's most distinctive claim and the one piece of differentiation from stock Pi. If the guard let me edit `foo.ts` because I happened to run `grep -c "x" foo.ts` — which means the model *saw zero matches and never read the file* — then the guard is not actually preventing hallucinated edits. It's preventing edits to files the model has never *named*. That's a much weaker invariant.

The author was clearly aware of the bash command extraction (it's a non-trivial 70-line function with a separate test section), but the name "Epistemic Read-Before-Write Guard" oversells what the extraction actually proves. *Naming* a file is not the same as *reading* a file. The model's own "attention to the file contents" is what the comment says the guard is grounding — but the implementation is grounding the model's *reference to the file path*.

**Concrete recommendation.** Two options, both good:

(a) **Rename the guard to "Referenced-Before-Write" or "Touched-Before-Write"** and document the actual semantics honestly. This is a one-line change with massive clarity benefit.

(b) **Make the bash extraction stricter.** Only count a file as inspected if the bash command actually reads from it, not just names it. Heuristic: the file appears as input to a command that opens files for reading (cat, less, head, tail, grep, sed, awk, rg, fd, find -exec cat), and ideally there's some output volume. The current code does the opposite — it counts any command that *names* a real file on disk, including `ls`, `stat`, `wc`, `file`, `chmod` — commands that don't read the file's content at all. The asymmetry: `ls` was rejected in my test, but I think that's because `ls` doesn't put a real file path as a non-flag positional token in the same way `grep foo.ts` does. The extraction rule needs to be principled, not accidental.

Either option is fine. The current state — name = "Epistemic Read-Before-Write" and behavior = "the file was named once somewhere" — is the worst combination.

#### Issue 2 (high): Failed verification leaves the file in a broken state

**The claim.** `docs/editing-and-verification.md`: *"Failed verification preserves the edit and reports the failure instead of silently rolling it back."* The post-edit verifier returns `FAIL!` and the agent gets told. The `edit` tool sets `isError: true` on the result.

**The actual behavior.** I deliberately introduced an unclosed `{` into a file via `edit`. Result:

```
FAIL!
syntax:failed
diagnostic,tests:not run
 -Syntax validation failed on never_read.ts: Unclosed '{' opened on line 2
  (still open at end of file)

[SYNTAX WARNING] Syntax validation failed on never_read.ts:
Unclosed '{' opened on line 2 (still open at end of file)
Please fix this syntax error.
```

The file on disk was left in the broken state. The agent is told it's broken, but the file is broken. The agent then has to (a) realize the file is broken, (b) call `/undo` (which uses `git reset --mixed` to roll back the commit, but in my test the auto-commit didn't even fire because verification failed), or (c) re-read the broken file (recording the inspection!) and try to fix it. In a long session where the model is making rapid edits, this is the difference between "the agent makes one bad edit and gets told" and "the agent makes one bad edit, gets told, and then has to spend 3-5 tool calls recovering."

**The argument in the docs.** *"instead of silently rolling it back"* — implying the alternative is silent rollback, which is also bad. The author is choosing between "the agent might not know the file is broken" and "the file is broken on disk."

**My counter-argument.** Both of those are bad. The third option — **atomic rejection** — is the right one: don't write the patch to disk until after the syntax check passes. The patcher reads the file into a buffer, computes the new content in memory, runs the syntax check on the *new* content, and only writes if the new content is clean. If the syntax check fails, return the error to the agent, but **leave the file unchanged**. The current ordering is: read → write → check. The correct ordering is: read → check → write. The patcher is doing the work in memory already (it has `originalContent` and `res.newContent`); it just needs to defer the `fs.writeFileSync` call until after `verifyEditedFile` returns.

This is a real safety improvement, not a stylistic one. The whole point of the per-edit syntax gate is to *prevent* the file from entering a broken state. The current implementation reports the breakage but does not prevent it. That makes the gate advisory rather than enforced.

**Concrete recommendation.** Reorder the operations in `edit_tool.ts`. Keep the buffer-based patch application, but run `verifyEditedFile` on the in-memory `patchRes.newContent` before calling `fs.writeFileSync` (or before returning the success result). The patcher needs an extra entry point like `applySurgicalPatchDry` that returns the new content without writing, or `applySurgicalPatchAtomic(file, search, replace, verifier)` that does the full chain.

If the maintainer genuinely thinks the current behavior is correct (preserve the broken edit, let the agent decide), then I would still ask for a single boolean parameter `atomic: true` on the `edit` tool, defaulting to `false` for backward compat, that enables the safer mode. The user should have the choice.

#### Issue 3 (medium): The auto-commit message contains a literal `[EMAIL]` placeholder

In `src/editing/git-verify.ts`:

```ts
"-c",
"user.email=[EMAIL]",
"commit",
```

This is a placeholder string, not a real email. It works in the sense that git accepts it (with a warning on most git versions), and the resulting commit author is `[EMAIL]`. But it's a small tell that the email was never filled in, and the commit history of any real project using this extension will have author `[EMAIL] <[EMAIL]>` on every `pi:` commit, which is then propagated to `git log`, blame, GitHub avatars, and any tooling that uses author info for filtering.

**Concrete fix.** Read `user.email` and `user.name` from git config (`git config user.email` / `git config user.name`) and fall back to a clearly-attributed placeholder like `pi-agent-kernel <pi-agent-kernel@local>`. Either way, never let `[EMAIL]` end up in commit history.

#### Issue 4 (medium): First-commit failure is silent

`autoCommitFile` returns `false` on any failure, including the very common case of "this is the first commit in a brand-new repo" (the file is staged, but `git commit` fails because there's no HEAD yet). The edit tool checks `verification.syntax.state === "clean"` before calling `autoCommitFile`, and reports `committed: false` in the details, but the visible message to the agent is just `OK!` — there's no signal that the change was not actually saved to git history.

This matters because `/undo` is implemented as `git reset --mixed HEAD~1`, which silently fails (and returns a non-actionable error) on a repo with no commits. The agent gets told "Successfully rolled back" if there was a previous commit, and gets a generic error otherwise — but it never finds out that the *current* edit was never committed in the first place, so there's nothing to roll back *to*.

**Concrete fix.** On first-commit failure, the auto-committer should run `git commit --allow-empty` or use `git -c ... commit` with the staged file (which it does) and then handle the "no HEAD yet" case explicitly by either doing the initial commit or by signaling clearly that this edit is in the working tree only and not in any commit yet.

#### Issue 5 (low): The `__default__` session id is a global

`getSessionId` returns `ctx?.sessionManager?.getSessionId?.() ?? "__default__"`. Every Pi session that doesn't have a UUID — which is "CLI single-session use and in-memory sessions" per the comment — shares the same `__default__` inspection set. So if I run the kernel once, exit, run it again, both runs share the "I have inspected these files" memory for the duration of the Node process.

The single-process CLI case is the documented use case, so this is intentional, but in an RPC setup where a long-lived Node process hosts many single-session invocations, the inspection set could grow without bound (the comment in `resetSession` acknowledges this for the multi-session case but `__default__` is the *one* case the comment does not cover because it can't tell from the id alone which default session is shutting down).

**Concrete fix.** When `getSessionId` returns the fallback, also include a process-unique id (e.g. a counter or a random suffix) so `__default__` becomes `__default__<pid>_<seq>__`. The reset path can then key on the same id. Or — and this is simpler — only use the singleton when running in a known-single-session mode, and key the guard on `ctx` itself in RPC mode.

#### Issue 6 (low): The README's "6-tier instruction precedence" claim is unsubstantiated

`README.md` says: *"Direct Behavioral Kernel (`src/index.ts`): Direct unblocked execution with strict epistemic grounding and 6-tier instruction precedence."* I read `src/index.ts` end to end. There is no implementation of a "6-tier instruction precedence" — the extension does not intercept or rewrite the system prompt, does not register a `before_agent_start` or `system_prompt` hook (it registers `session_start`, `session_shutdown`, `tool_call`, `tool_result`, `session_before_compact`), and the system prompt that arrives at the model is whatever the host Pi session provides. The "6-tier" claim is marketing copy, not engineering.

**Concrete fix.** Either implement the 6-tier precedence (and document it in `docs/` so reviewers can find it), or remove the claim from the README. Documentation promises that aren't backed by code erode trust on the things that *are* backed by code.

#### Issue 7 (low): The `search_index.ts` module loads `@huggingface/transformers` lazily but the disk-cache test reads it at the wrong time

This is a tiny thing. Section 10 of the test suite (`isModelCached: true`) checks that the embedder is detectable on disk. That's good. But the `preloadModel` call (in `src/index.ts`) is gated by `if (eff === "hybrid" || eff === "full")` and a `notify("Lean mode active …")` short-circuit. On first run, the model is downloaded on demand, and a `Lean`-mode user who switches to `hybrid` mid-session will see a multi-second blocking pause while the model loads. The widget shows "Engine: Loading embedding model…" so it's not silent, but the model is loaded on the *foreground* thread, not in a worker, so the TUI will freeze for the duration. For a 768-dim model on a slow disk this can be 5-10 seconds.

**Concrete fix.** Either (a) start loading the model in a worker as soon as the user picks any non-lean profile, or (b) document the foreground-loading tradeoff and offer a `--preload-embeddings` flag for users who want to pay the cost up front. The current design is fine for "set it once and forget it" workflows and is genuinely bad for "tinker with profiles" workflows.

#### Issue 8 (low): `applySurgicalPatch` writes to disk on a `success: true` result, but `success` does not mean "the new content is valid"

This is a sub-case of Issue 2 but worth calling out separately. The patcher's contract is "I successfully located your search block and replaced it" — not "the new file is well-formed." The two-step gate (patcher success → syntax check) is split across two files (`patch.ts` and `post_edit_verification.ts`) and the contract between them is implicit. A future contributor adding a new patcher strategy would have to read both files to understand the gate ordering.

**Concrete fix.** Add a single doc comment to `PatchResult` in `patch.ts` that says: *"success means the search block was located and the replacement was composed. It does not imply the result is syntactically valid; that check is the caller's responsibility (see `post_edit_verification.ts`)."* Better: see Issue 2's fix, which makes this concern moot.

#### Issue 9 (style): The 700-line `index.ts` `unifiedHybridExtension` function is doing too much

`src/index.ts` is 705 lines, all inside a single function. It registers 7 tools, 5+ slash commands, the footer, the indexing pipeline, the tool-call preflight, the tool-result interceptor, the session lifecycle hooks, and a custom fallback select menu that is itself ~80 lines of string-concatenated options. This works but it's at the limit of what's reviewable in one sitting.

The pattern is already broken in the right direction: each tool is in its own `src/tools/*.ts` file with a `register*Tool` function. The slash commands, the indexing pipeline, and the tool-result interceptor are not yet split out. Pulling `setupUnifiedFooter`, `triggerBackgroundIndexing`, the `/engine` command handler, and the `tool_result` interceptor into their own files would reduce `index.ts` to a thin wiring layer.

**Concrete fix.** Extract:
- `src/indexing/background_index.ts` — `triggerBackgroundIndexing`, `getSearchIndex`, the lean/hybrid/full branching
- `src/commands/engine.ts` — the `/engine` command handler
- `src/commands/lsp.ts` — the `/lsp` command handler
- `src/commands/oracle.ts` — the `/oracle` command handler
- `src/commands/undo.ts` — the `/undo` command handler (which currently is inlined in the `pi.on("command")` block)
- `src/interceptors/tool_result.ts` — the `tool_result` post-processor
- `src/interceptors/tool_call.ts` — the `tool_call` preflight

That should bring `index.ts` down to ~200 lines of wiring.

#### Issue 10 (style): The `agent-kernel` name and the `pi-agent-kernel` package name don't match

The directory is `agent-kernel/`, the `package.json` `name` is `pi-agent-kernel`, the README refers to it as `agent-kernel` ("`agent-kernel` is designed for bare-minimum token usage …"), and the `pi-package` keyword is in the `package.json`. None of these are wrong on their own, but a contributor who is told "go work on agent-kernel" will be confused about which name to put in their commit messages. Pick one (I'd vote `pi-agent-kernel` since that's the package name) and use it everywhere.

## What I would tell a friend considering this extension

**Use it if** you are a Pi power user who (a) works in long sessions where context accumulates, (b) writes enough code that the auto-commit / undo flow is a meaningful safety net, (c) wants an in-TUI retrieval engine that is genuinely better than `rg` for "find me the function that does X", and (d) is willing to read the source to understand the actual semantics of the epistemic guard rather than trusting the name.

**Wait if** you are new to Pi, or you primarily do read-only work (research, code review) where the patcher and the guard don't apply, or you run Pi in a setup where the foreground embedding model load will be a real cost. The lean profile is good but the default user will get the auto-detect path and may not realize what they're paying for.

**Don't expect** that installing this extension will make your agent "epistemically grounded" in the strong sense the name suggests. It will make your agent *reference-tracked* — which is a real improvement, and a meaningful one, but it is not the same thing.

---

## Final verdict

This is a substantial, well-tested, opinionated extension that has earned its place. The author has thought carefully about the failure modes of LLM-driven editing and has built specific defenses against them (the syntax gate, the auto-commit, the per-edit verification, the output clamping, the spillover file, the per-session guard scoping). Most of those defenses work. Two of them — the epistemic guard's actual semantics, and the failed-verification leave-broken-on-disk policy — are not what their names suggest, and the project would be meaningfully better by fixing both.

If I were the maintainer, I would do these five things, in order:

1. **Rename or fix the epistemic guard** (Issue 1). The current name is a liability.
2. **Reorder edit to be atomic: read → check → write** (Issue 2). This is the single biggest safety improvement available.
3. **Fix the `[EMAIL]` placeholder** (Issue 3). Five-minute change, real impact.
4. **Document or remove the "6-tier instruction precedence" claim** (Issue 6). Either implement it or stop claiming it.
5. **Split `index.ts` into wiring + per-concern files** (Issue 9). A pure refactor; the tests will tell you when you're done.

The first two are correctness. The third is hygiene. The fourth is honesty. The fifth is taste. All of them are smaller than the work that has already gone into the extension, and the project will be better for each.
